\subsection{Deployment and Operations}\label{sec:deployment}
\subsubsection{Local} The whole system runs in Docker as three Compose projects on one network, one for the infrastructure (databases, Kafka, Ollama and a job that downloads the models, Keycloak), one for the four services and one for the frontend. One multi-stage Dockerfile builds any service, and the same images serve the cloud. A \code{justfile} starts the projects in order and waits for each to be healthy, since Compose cannot order separate projects.

\subsubsection{Kubernetes on GCP} Everything is driven from a management container holding Terraform, Ansible, \code{kubectl} and \code{gcloud}. Terraform creates, in a separate stack that outlives the VMs, one data disk per worker and a static IP (Section~\ref{sec:advanced}), and then a VPC, firewall rules and three Ubuntu~24.04 VMs in \code{europe-west4-b}, a control plane (\code{e2-standard-2}) and two workers (\code{e2-standard-4}). Four Ansible playbooks then prepare the nodes (containerd, kubeadm), create the cluster with Calico as pod network, install the platform with Helm (the Strimzi Kafka operator, kube-prometheus-stack and the volumes), and deploy the application from manifest templates, with a PostgreSQL StatefulSet per database with a metrics sidecar, Kafka with three brokers and topics replicated three times, Ollama, Keycloak, a Deployment per service with health probes, and NetworkPolicies so that each database accepts only its own service. NGINX runs on the worker that owns the static IP, and every other port stays closed to the Internet. Secrets are generated on the first run and kept out of git, and every step can be re-run without changing what is already right. A deployment from nothing takes about 25 minutes:

{\footnotesize\begin{verbatim}
just images docker.io/<user> v1 # push images
just mgmt-start && just mgmt    # mgmt shell
just all              # VMs, cluster, app
just stop | start | destroy
\end{verbatim}}
\noindent The repository's \code{README.md} and \code{infra/README.md} give every step, including the one-time Google Cloud setup.

\subsubsection{Monitoring} Prometheus scrapes, every 15\,s, each service's Micrometer metrics, the databases' and NGINX's exporters, Kafka's lag and the nodes. Beyond the standard HTTP and JVM metrics, each service records application metrics, such as searches and whether they found anything, profile changes, recommendation requests by kind and outcome (including those answered without the model), the time from a request to its answer, jobs waiting in Kafka, and each model call's duration and tokens, since Ollama has no metrics of its own. A provisioned Grafana dashboard, \emph{Movies}, is built on them, and is served at \code{/grafana}, while Prometheus itself is not public. Fluent Bit, on every node, collects each container's log, and Loki aggregates them for 7~days, so they can be searched in Grafana across pods and restarts. Prometheus also evaluates our alert rules (Table~\ref{tab:alerts}), besides kube-prometheus-stack's defaults, and Grafana lists them by state. There is no Alertmanager, so alerts are not sent anywhere.
