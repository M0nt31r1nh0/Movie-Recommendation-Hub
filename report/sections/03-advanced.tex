\section{Advanced Component: Persistent State}\label{sec:advanced}

\subsubsection{Goal}
All VMs of the deployment (control plane and workers) can be stopped, as when the cloud budget is paused overnight, and started again later; or destroyed altogether (\code{terraform destroy}) and recreated, with a new Kubernetes cluster, days later. In both cases, after the cluster converges, every user, profile, follow, watched movie and cached recommendation must still be there, without re-seeding or manual steps; and the very first deployment, with no data yet, must start empty through the same commands. Storage must be self-hosted inside the cluster rather than a managed database service, which also avoids vendor lock-in.

\subsubsection{Stateful components}
Table~\ref{tab:state} lists the state to preserve. Locally, every component keeps its data in its own named Docker volume, which survives \code{docker compose down}; in the cluster, each one gets a PersistentVolumeClaim whose volume is a folder on a worker's data disk. Keycloak stores the realm and users in PostgreSQL rather than in its embedded H2 store. Everything else (APIs, worker, frontend, NGINX) is stateless and can be rescheduled freely.

\subsubsection{Storage options}
Each database runs as a single-replica \code{StatefulSet} whose \code{volumeClaimTemplate} binds a PersistentVolumeClaim (PVC) to a PersistentVolume (PV)~\cite{k8s-pv}. The question is what backs the PVs:
\begin{itemize}
\item \emph{Local PVs} on a disk of a given node: simple and fast, but each pod is pinned to that node through node affinity, and the data has no replica.
\item \emph{Longhorn}~\cite{longhorn}: a CNCF block-storage system that runs as a CSI driver on the cluster nodes, with dynamic provisioning, replicas on several nodes, snapshots and backups. It requires \code{open-iscsi} on the nodes and some CPU and memory overhead.
\item \emph{Rook-Ceph}: more capable, but needs raw disks and far more resources than a few small VMs can spare.
\item \emph{NFS server VM}: easy to set up, but a single point of failure, and PostgreSQL over NFS is fragile (locking, \code{fsync}).
\end{itemize}
We use local PVs, which add no components or memory overhead to small VMs. Our first version had Rancher's local-path-provisioner create them on the nodes' boot disks: they survived stopping the VMs, but not a \code{terraform destroy}, which deletes the boot disks, nor a new cluster, in which the provisioner would create new, empty folders with new names. We therefore moved them to \emph{data disks}: one Compute Engine persistent disk per worker, which Terraform manages apart from the VMs, mounted at \code{/mnt/data}, with one statically declared PV per claim. The trade-off remains that each pod is pinned to its worker and its data has no replica (a disk is zonal, and a PV is on one disk); Longhorn would lift that at the cost of extra components on every node, and Compute Engine's CSI driver would let pods follow their disks between nodes, at the cost of giving the cluster cloud credentials.

\subsubsection{Design}
Persistence rests on six measures. (i)~\emph{Data outlives the VMs}: the data disks and the static IP are created by a second Terraform stack with its own state, which the VMs' stack only looks up by name and attaches. So \code{terraform destroy} of the VMs (\code{just destroy}) cannot delete them, and only an explicit \code{just destroy-data} does. Before applying, \code{just persistent} imports any disk or address that exists in the project but not in its state (an earlier deployment's, or a teammate's), so it creates them only the first time. The address is kept because Keycloak's realm, stored in its database, names it in its login redirects. A worker formats its data disk only if it has no filesystem, and kubelet waits for the mount (\code{RequiresMountsFor}), so no pod ever starts on the empty folder beneath it.
(ii)~\emph{Volumes are found again by name}: there is no dynamic provisioner. The platform playbook declares one local PV per claim, with \code{Retain}, a \code{claimRef} to the claim's namespace and name, a node affinity to its worker, and a fixed folder, \code{/mnt/data/<namespace>/<claim>}. StatefulSet, Strimzi and Prometheus claims have deterministic names (e.g.\ \code{data-movies-db-0}), so the same claim in a new cluster binds to the same folder.
(iii)~\emph{Initialisation is idempotent}: PostgreSQL runs \code{initdb} only on an empty folder, Flyway applies only pending migrations, the playbook loads the catalogue dump only the first time, Keycloak imports its realm only if absent, and Ollama downloads only missing models. Kafka needs one more step: Strimzi gives a new \code{Kafka} resource a new cluster ID, which brokers refuse when their data was written under another. On a new cluster, the playbook reads \code{cluster.id} from broker~0's \code{meta.properties} on the disk; if there is one, it creates the resource with reconciliation paused, writes that ID to its status and resumes it, following Strimzi's recovery procedure. The generated passwords are kept in a git-ignored folder, and the playbook refuses to deploy over a database whose password is missing from it.
(iv)~\emph{Results are stored in PostgreSQL}, not in memory, and pending jobs wait in Kafka, so users get their recommendations right after a restart.
(v)~\emph{The public address is stable}, as explained in (i), and so are Keycloak's tokens' issuer and the TLS certificate's name.
(vi)~\emph{Repeatable stop and start}: \code{just stop} and \code{just start} change one Terraform variable, \code{vm\_state}, which the Google provider turns into the Compute Engine stop and start calls for each VM. A stopped VM keeps its disks and costs only the disks and the static address. GCE releases ephemeral public addresses while a VM is stopped, and after a start the master and worker2 can get different ones (in our runs they swapped). So \code{start} runs Terraform twice, first for the VMs alone and then in full, to read the new addresses and rewrite the Ansible inventory, and it points the kubeconfig at the master's new address while checking the API certificate against the name \code{kubernetes}, which kubeadm includes. It then waits for the nodes, Kafka, every StatefulSet and Deployment, and for the application to answer. We rely on GCE's clean guest shutdown instead of scaling the pods down first.

\subsubsection{Validation}
(1)~Create users through the UI, set genres, watched movies and follows, and let the agent cache recommendations. Record the row counts of each database, the finished recommendation requests, the Keycloak user list, Kafka's topics, the models and the volumes (\code{just snapshot}). (2)~Stop all VMs (\code{just stop}). (3)~Start them (\code{just start}), which waits until all nodes and pods are \code{Ready} and the application answers. (4)~Record the state again and compare (\code{just compare}), log in as an existing user, and check that stored recommendations are served without inference. Results: after a full stop and start, the databases (movies, profiles, recommendations, Keycloak), Kafka's topics, the models, Prometheus's history and all volumes came back unchanged, existing users logged in, and their follows, watched movies and recommendations were served. The application answered \TODO{N}\,s after \code{just start}; the stop takes about 1.5\,min. A recommendation being computed when the VMs stopped failed (\emph{Connection was closed}) and its user was told so; the requests still waiting in Kafka were processed once the worker was back, and a failed profile request is retried by the background agent after its back-off. The first minute after a start shows transient errors (Keycloak and Kafka not yet reachable) that clear without intervention. (5)~Repeat with \code{just destroy} and \code{just all} instead of stop and start: a new cluster on new VMs, with the same data disks. Before destroying, we also wrote a marker row in each database and three messages to a Kafka topic, two of them consumed by a consumer group. The destroy took about 3\,min and left only the two data disks and the static address. On redeploy, \code{just persistent} found and imported them even with its state file removed, as a teammate's would be; the workers reported their disks in use since the first deployment, the playbook detected the four databases' data, skipped the catalogue import, and gave the new Kafka resource the cluster ID read from the brokers' disk. The snapshots were identical, every marker row was there, the topic still held its three messages, and the consumer group resumed with the third. A second run also covered monitoring: queried for the same past moment, Prometheus returned the same values before and after (its oldest sample unchanged), and Grafana's database, kept on its own volume, still had the admin user and organisation with their original creation dates. Rebuilding everything on new VMs took about 25\,min (the playbooks 23\,min). While destroyed, the data disks and the static address cost about 15~USD a month. The limits are those of local volumes: the data survives the loss of the VMs, but not the loss of a data disk, and pods cannot move to another worker.
