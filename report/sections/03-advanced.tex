\section{Advanced Component: Persistent State}\label{sec:advanced}

\subsubsection{Goal}
All VMs of the deployment (control plane and workers) can be stopped, as when the cloud budget is paused overnight, and started again later. After the cluster converges, every user, profile, follow, watched movie and cached recommendation must still be there, without re-seeding or manual steps. Storage must be self-hosted inside the cluster rather than a managed database service, which also avoids vendor lock-in.

\subsubsection{Stateful components}
Table~\ref{tab:state} lists the state to preserve. Locally, every component keeps its data in its own named Docker volume, which survives \code{docker compose down}; in the cluster, each one gets a PersistentVolumeClaim. Keycloak stores the realm and users in PostgreSQL rather than in its embedded H2 store. Everything else (APIs, worker, frontend, NGINX) is stateless and can be rescheduled freely.

\subsubsection{Storage options}
Each database runs as a single-replica \code{StatefulSet} whose \code{volumeClaimTemplate} binds a PersistentVolumeClaim (PVC) to a PersistentVolume (PV)~\cite{k8s-pv}. The question is what backs the PVs:
\begin{itemize}
\item \emph{Local PVs} on a disk of a given node: simple and fast, but each pod is pinned to that node through node affinity, and the data has no replica.
\item \emph{Longhorn}~\cite{longhorn}: a CNCF block-storage system that runs as a CSI driver on the cluster nodes, with dynamic provisioning, replicas on several nodes, snapshots and backups. It requires \code{open-iscsi} on the nodes and some CPU and memory overhead.
\item \emph{Rook-Ceph}: more capable, but needs raw disks and far more resources than a few small VMs can spare.
\item \emph{NFS server VM}: easy to set up, but a single point of failure, and PostgreSQL over NFS is fragile (locking, \code{fsync}).
\end{itemize}
We use local PVs, provided by Rancher's local-path-provisioner, which the platform playbook installs and sets as the default \code{StorageClass}. It adds no components or memory overhead to small VMs, and the volumes live on the nodes' boot disks, which survive stopping the VMs. The trade-off is that each pod stays pinned to its node and its data has no replica: state survives a restart of the cluster, but not the loss of a VM or a \code{terraform destroy}. Longhorn would lift that limit at the cost of extra components on every node.

\subsubsection{Design}
Persistence rests on five measures. (i)~\emph{Volumes outlive pods}: each database and each Kafka broker is a StatefulSet with a \code{volumeClaimTemplate} (Kafka's claims are kept even if the cluster resource is deleted), and the models and Prometheus data have their own claims. (ii)~\emph{Initialisation is idempotent}: Flyway applies only pending migrations, the playbook loads the catalogue dump only the first time, and Keycloak imports its realm only on its first start; the generated passwords are kept in a git-ignored folder, so that running the playbooks again reuses the values the databases were created with. (iii)~\emph{Results are stored in PostgreSQL}, not in memory, and pending jobs wait in Kafka, so users get their recommendations right after a restart. (iv)~\emph{The public address is stable}: the edge node keeps a reserved static IP, which Keycloak's tokens, the login redirects and the TLS certificate all name.
(v)~\emph{Repeatable stop and start}: \code{just stop} and \code{just start} change one Terraform variable, \code{vm\_state}, which the Google provider turns into the Compute Engine stop and start calls for each VM. A stopped VM keeps its disks, and with them every volume, and costs only the disks and the static address. GCE releases ephemeral public addresses while a VM is stopped, and after a start the master and worker2 can get different ones (in our runs they swapped). So \code{start} runs Terraform twice, first for the VMs alone and then in full, to read the new addresses and rewrite the Ansible inventory, and it points the kubeconfig at the master's new address while checking the API certificate against the name \code{kubernetes}, which kubeadm includes. It then waits for the nodes, Kafka, every StatefulSet and Deployment, and for the application to answer. We rely on GCE's clean guest shutdown instead of scaling the pods down first.

\subsubsection{Validation}
(1)~Create users through the UI, set genres, watched movies and follows, and let the agent cache recommendations. Record the row counts of each database, the finished recommendation requests, the Keycloak user list, Kafka's topics, the models and the volumes (\code{just snapshot}). (2)~Stop all VMs (\code{just stop}). (3)~Start them (\code{just start}), which waits until all nodes and pods are \code{Ready} and the application answers. (4)~Record the state again and compare (\code{just compare}), log in as an existing user, and check that stored recommendations are served without inference. Results: after a full stop and start, the databases (movies, profiles, recommendations, Keycloak), Kafka's topics, the models, Prometheus's history and all volumes came back unchanged, existing users logged in, and their follows, watched movies and recommendations were served. The application answered \TODO{N}\,s after \code{just start}; the stop takes about 1.5\,min. A recommendation being computed when the VMs stopped failed (\emph{Connection was closed}) and its user was told so; the requests still waiting in Kafka were processed once the worker was back, and a failed profile request is retried by the background agent after its back-off. The first minute after a start shows transient errors (Keycloak and Kafka not yet reachable) that clear without intervention. The limits stay as stated above: the data survives a stop, not a \code{terraform destroy} or the loss of a VM.
