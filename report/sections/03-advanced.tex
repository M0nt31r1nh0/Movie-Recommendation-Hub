\section{Advanced Component: Persistent State}\label{sec:advanced}

\subsubsection{Goal} All VMs can be stopped and started again, or destroyed altogether (\code{terraform destroy}) and recreated days later as a new Kubernetes cluster. In both cases every user, profile, follow, watched movie and stored recommendation must still be there, with no manual steps, while a first deployment with no data starts empty through the same commands. The data stays on disks attached to the VMs, so the storage is self-hosted rather than an external managed service, and recovery does not depend on keeping the Terraform state. Table~\ref{tab:state} lists the state to keep, since the APIs, the worker, the frontend and NGINX are stateless.

\subsubsection{Storage choice} Each database is a one-replica StatefulSet whose claim binds to a PersistentVolume~\cite{k8s-pv}. We back the volumes with \emph{local} PVs on a Compute Engine data disk per worker, which adds no components to small VMs. Our first version used local-path-provisioner on the boot disks, which survived stopping the VMs but not \code{terraform destroy}, which deletes boot disks, nor a new cluster, where it would create new empty folders. Longhorn~\cite{longhorn} would replicate volumes across nodes at the cost of an extra storage system on every node. Rook-Ceph needs far more resources, an NFS VM is a single point of failure and fragile under PostgreSQL, and the GCE CSI driver would let pods follow their disks between nodes but needs cloud credentials in the cluster. The trade-off we accept is that each pod is pinned to its worker and its data has no replica.

\subsubsection{Design} (i)~\emph{Data outlives the VMs.} The data disks and the static IP belong to a second Terraform stack with its own state, which the VM stack only looks up by name, so destroying the VMs cannot delete them, and only an explicit \code{just destroy-data} does. Before applying, \code{just persistent} imports any disk or address that exists in the project but not in its state, so the first deployment creates them and later ones reuse them. A worker formats its disk only if it is blank, and kubelet starts only once it is mounted. (ii)~\emph{Volumes are found again by name.} There is no dynamic provisioner, so the platform playbook declares one PV per claim, with \code{Retain}, a \code{claimRef} to the claim's namespace and name, a node affinity and a fixed folder, so the same claim in a new cluster binds to the same data. (iii)~\emph{Initialisation is idempotent.} PostgreSQL runs \code{initdb} only on an empty folder, Flyway applies only pending migrations, the playbook loads the catalogue only once, Keycloak imports its realm only if absent, and Ollama downloads only missing models. Kafka needs one more step, since Strimzi gives a new cluster a new ID that brokers refuse, so the playbook reads the old ID from the disk and gives it back to the new Kafka resource, following Strimzi's recovery procedure. (iv)~\emph{Results live in PostgreSQL} and pending jobs in Kafka. (v)~\emph{Stop and start.} \code{just stop} and \code{just start} change one Terraform variable, which Google's provider turns into Compute Engine stop and start calls. Stopped VMs cost only their disks and the static IP. Since stopped VMs lose their ephemeral addresses, \code{start} rereads them, rewrites Ansible's inventory, points the kubeconfig at the new master address, and waits until the application answers.

\subsubsection{Validation} A snapshot script records each database's row counts, the finished recommendations, Keycloak's users, Kafka's topics and consumer offsets, the models, Prometheus's oldest sample, Grafana's users and the volumes, and a compare script diffs two snapshots. After a full stop and start, the snapshots were identical, existing users logged in, and their data and recommendations were served. The application answered 239\,s after \code{just start}, and \code{just stop} takes about 1.5 minutes. A recommendation being computed when the VMs stopped failed and its user was told so, while queued ones were processed afterwards. We then destroyed every VM and redeployed on the same disks, with marker rows in each database and messages in a Kafka topic, and the snapshots were identical, every marker was there, the consumer group resumed where it stopped, and Prometheus returned the same historical values. Rebuilding took about 25 minutes, and while destroyed the disks and address cost about 15~USD a month. The limits are those of local volumes, since the data survives losing the VMs but not losing a data disk.
