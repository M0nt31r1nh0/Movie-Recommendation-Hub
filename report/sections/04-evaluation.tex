\section{Evaluation}\label{sec:eval}

\subsubsection{Method} We measured throughput and latency as the number of concurrent clients grows, with k6~\cite{k6} running in a pod on the control-plane node, which runs no application pods, so it shares no CPU with the system it measures and adds no wide-area latency. Each client logs in as its own test user through a temporary Keycloak client and then loops, sending one action from a weighted mix and waiting 0.5--1.5\,s (1\,s on average). The mix is browsing the catalogue (35\%), search (25\%), a movie page (10\%), a profile and its watched movies (15\%), marking and unmarking a movie as watched (5\%) and reading \emph{Recommended for you} from the cache (10\%), about 1.2 requests per action, all through NGINX's public address. On-demand recommendations are left out, because one takes the model about 4.5 minutes on these CPUs, which is why they are asynchronous. Each step ramps up for 30\,s, warms up for 60\,s and is measured for 180\,s. Token requests and the warm-up are excluded, and each step ran three times. The cluster is that of Section~\ref{sec:deployment}, with one replica per service, and Prometheus recorded the CPU of every pod and node.

\subsubsection{Results} Table~\ref{tab:eval} and Fig.~\ref{fig:eval} show two regimes. Up to 100 clients the system is lightly loaded and throughput grows linearly, about 1.17\,req/s per client, which is what a closed loop with a 1\,s think time and short responses predicts (1.2 requests per second of think time), and the median latency stays near 12\,ms. At 200 clients throughput reaches its peak, about 216\,req/s, and latency starts to rise (p95 291\,ms). Beyond that, adding clients adds no throughput, which stays near 200--206\,req/s, while every percentile grows, and at 400 clients the median is 0.93\,s and p99 5.8\,s. The system slows down rather than fails, with at most 0.04\% errors, and these were \code{500}s from \code{GET /recommendations/me}, whose call to the Movies API for titles has no error handling, at low load as well as high.

\subsubsection{Bottleneck} The limit is the CPU of worker1, at 97\% with 200 clients and 100\% with 300. The scheduler had placed every stateless Deployment on worker1, next to the four databases, so worker2 stayed at 8\% and the cluster's second worker added almost nothing. The largest consumer is the movies database, which reached 2.3 of worker1's 4 vCPUs, because 70\% of the actions are catalogue reads, and search runs full-text and trigram queries. The Movies API itself used about 0.5 cores. The master, running k6, never exceeded 38\% CPU, so the generator did not limit the results. Spreading the stateless pods across workers (topology spread constraints), adding replicas, and caching or replicating the catalogue database are the direct remedies, while horizontal autoscaling, the advanced option we did not take, would add replicas only if they could be scheduled on the idle worker.
